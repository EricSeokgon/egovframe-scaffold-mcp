# 개인정보 흐름·보호조치 점검 설계 (`check_egovframe_privacy`, v1.21.0)

## 1. 문제

공공 사업은 개인정보 영향평가·감리에서 "어떤 개인정보를 어느 테이블에 두고 어느 화면이 다루는가"(개인정보 파일·흐름표)와 "고유식별정보·비밀번호를 암호화해 저장하는가"를 문서로 냅니다. 지금은 DDL 과 화면을 사람이 대조합니다. 2026-11-13 실측: 공통컴포넌트(v5.0.7·main)의 사용자 관리(`uss.umt`)는 비밀번호를 `EgovFileScrty.encryptPassword` 로 해시하지만 주민등록번호(`IHIDNUM`)는 `#{ihidnum}` 그대로 INSERT·UPDATE 하고, 게시물·댓글 비밀번호도 평문으로 들어갑니다. 조립한 프로젝트는 이것을 그대로 물려받습니다.

## 2. 선행 조사가 정한 것

- **컬럼 이름이 표준 용어다.** `IHIDNUM`(주민등록번호)·`MBTLNUM`(이동전화)·`EMAIL_ADRES`·`BRTHDY`·`ADRES` 처럼 공통 표준 용어를 쓰므로 이름 사전으로 찾을 수 있습니다. 실제 데이터를 볼 필요가 없습니다.
- **흐름은 이미 있다.** v1.14 구조 지도(`buildProjectMap`)가 테이블 → 매퍼 문장 → DAO → Service → Controller → URL → 화면을 잇습니다. 컬럼 사전만 더하면 흐름표가 됩니다.
- **암호화는 Service 에서 한다.** 공통컴포넌트는 매퍼에 넘기기 전에 VO 의 값을 바꿉니다(`vo.setPassword(EgovFileScrty.encryptPassword(…))`). 그래서 "쓰는 문장을 부르는 경로의 Java 파일에 그 필드와 암호화 호출이 가까이 있는가"로 판정할 수 있습니다.

## 3. 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 규칙은 데이터 | `catalog/privacy-rules.json` — 항목 14종(`columns` 정규식, 컬럼 이름 전체에 대조·대소문자 무시)과 등급 4종(고유식별정보·인증정보·금융정보는 `encryptAtRest`), 호출 사전 `cryptoCalls`·`sqlCryptoFunctions`·`maskCalls`·`logCalls`, 출처 | 기관마다 컬럼 이름 규칙·암호화 솔루션(DB 암호화 함수)이 다르다 — v1.23 규칙 팩이 더할 자리 |
| 컬럼 출처 | DDL 의 `CREATE TABLE`(적재 데이터 스크립트 `dml`·`_DML_`·`data*.sql` 제외) + 매퍼 문장의 컬럼. DB 별 사본은 한 번만 | DDL 이 없는 프로젝트도 매퍼에서 찾는다. 공통컴포넌트는 DDL 스크립트가 945개라 건너뛸 것을 정해야 3초대 |
| 이름 대조 | 컬럼 이름 **전체**에 대조하고 접두·접미 토큰을 사전에 명시 | `PASSWORD_HINT`·`ADRES_CODE` 같은 비슷한 일반 컬럼을 넣지 않기 위해(단위 테스트의 음성 사례) |
| 흐름표 | 테이블마다 읽기·쓰기 문장 수와 Service·Controller·URL·화면 | 영향평가의 "처리 흐름"에 그대로 옮길 수 있는 단위 |
| 평문 저장(높음) | 암호화 대상 등급의 컬럼에 `#{…}` 로 쓰는 INSERT·UPDATE 인데 (1) 문장에 SQL 암호화 함수가 없고 (2) 호출 경로(DAO·Service·Controller, 생성자 주입은 DAO 단순 이름으로 보완)의 Java 파일에 그 필드 이름과 암호화 호출이 ±1줄 안에 없음 | 공통컴포넌트의 실제 모양(`setPassword(encrypt…(getPassword()))`)을 통과시키고 `IHIDNUM` 을 잡는 가장 좁은 조건 |
| 화면 노출(중간) | 고유식별정보 필드를 JSP·Thymeleaf 가 출력하는데 그 줄에 마스킹 호출이 없음. 입력 필드(`<input>`·`form:`·`th:field`)는 제외 | 등록·수정 폼은 값을 받아야 한다. 목록·상세 출력만 본다 |
| 로그 노출(중간) | 암호화 대상 필드를 로그·`System.out` 으로 출력 | 로그는 접근 통제 밖으로 나간다 |
| DB 사본 | 같은 문장의 DB 별 매퍼는 한 건으로 묶고 `variants` 에 개수 | 공통컴포넌트는 DB 8종 사본이 있어 그대로 세면 7건이 56건 |
| 예외 | `.egovframe-privacy-ignore.json` — 보안약점·운영 점검과 같은 형식·같은 로더, `rule` 은 종류(`plaintext-storage`·`screen-exposure`·`log-exposure`) | DB 암호화 솔루션(TDE·플러그인)으로 처리하는 기관은 사유·검토자를 남기고 제외 |
| 평가서·납품 | 평가서 4절 아래 「개인정보」(테이블·컬럼·높음·중간), 납품 패키지 항목 `privacy`(기본 포함 아님): `privacy.md`·`privacy.json`·`personal-data-files.csv` | 개인정보를 다루지 않는 프로젝트의 패키지를 바꾸지 않는다(기본 include 그대로) |
| CLI | `privacy`, `--fail-on high>0` 등(지표 `tables`·`columns`·`uniqueIdTables`·`high`·`medium`) | 다른 점검 명령과 같은 모양 |

범위 밖: 법 해석·영향평가서 작성, 실제 DB 데이터 스캔, 자동 암호화 적용(키 관리·기존 데이터 이관은 기관 결정), 첨부 파일 안 개인정보.

## 4. 한계 (결과에 `notes` 로 표시)

- **이름 기반**: 표준 용어를 따르지 않는 컬럼(`COL1`·`ETC`)은 찾지 못하고, 이름만 비슷한 컬럼이 들어올 수 있습니다. 사전은 `catalog/privacy-rules.json` 에서 고칩니다.
- **파일 단위 판정**: 암호화 호출은 호출 경로 파일 안에서 필드 이름 근처에 있는지만 봅니다. 한 파일에 메서드가 여럿이면, 등록은 암호화하고 수정은 하지 않아도 통과합니다.
- **DB·저장소 암호화는 모른다**: TDE·컬럼 암호화 플러그인·MyBatis TypeHandler 로 처리하면 평문 저장으로 나옵니다 → 예외 파일.
- **접근기록 연결**(조회 URL 에 로그 컴포넌트·인터셉터가 걸렸는가)은 기획에 있었지만 넣지 않았습니다. 인터셉터 매핑의 정적 해석이 불확실해 오탐이 많았습니다.

## 5. 검증

- 게이트 `test:privacy`(24단언, 오프라인): 사전 양성·음성·등급, DDL·매퍼 컬럼 수집, 흐름표 연결, 평문 저장 판정(암호화 호출·SQL 함수·selectKey 문장), 화면·로그 노출, DB 사본 묶음, 예외 파일, CSV, MCP 등록·구조화 출력.
- CI 통합 `test:privacy-live`(13단언): 공통컴포넌트 v5.0.7 — 개인정보 테이블 32·컬럼 91·고유식별정보 테이블 2, 높음 7(주민등록번호 4 + 게시물·댓글 비밀번호 3), 사용자 비밀번호 통과. 보고한 문장을 원본 XML 에서 다시 읽어 컬럼·바인딩이 있고 SQL 암호화가 없음을 독립 확인. 공식 템플릿 6종 수치, 10초 이내(실측 3.2–3.5초).

## 6. 규칙 갱신 절차

1. 공통컴포넌트 새 태그가 나오면 `test:privacy-live` 의 수치가 달라지는지 봅니다(달라지면 새 컬럼·수정된 경로).
2. 새 컬럼 이름은 `items[].columns` 에, 새 암호화 유틸·DB 함수는 `cryptoCalls`·`sqlCryptoFunctions` 에 더하고 `surveyedAt` 을 고칩니다.
3. `test:privacy` 의 음성 사례(비슷한 일반 컬럼)가 그대로 통과하는지 확인합니다.
