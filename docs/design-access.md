# 접근 통제 점검 설계 (`check_egovframe_access`, v1.24.0)

## 1. 문제

로그인하지 않거나 남의 글 번호를 넣어도 수정·삭제가 되는 결함(부적절한 인가 — CWE-285·CWE-862·CWE-639)은 보안약점 진단의 단골 지적입니다. 정규식 한 줄로는 못 찾습니다 — "있어야 할 검증이 없다"는 것이기 때문입니다. 공통컴포넌트는 v5.0.6 → v5.0.7 사이에 컨트롤러 핸들러 145개의 검증을 올렸습니다(소유권 검증 32 → 146개). 5.0.6 이하를 조립한 프로젝트와, 그 패턴을 따라 쓴 프로젝트 코드에 같은 결함이 있습니다. 감리는 "화면·URL 별 권한"을 표로 요구합니다.

## 2. 선행 조사가 정한 것

- **수정은 핸들러 첫머리의 한두 줄이다.** `EgovAuthorizationHelper.assertLoginUser()`·`assertAdmin()`·`assertOwner(vo.getFrstRegisterId())`, `EgovUserDetailsHelper.isAuthenticated()`·`getAuthorities()`, 등록자 ID 와 로그인 사용자의 `equals` 비교. 호출 이름 사전으로 찾을 수 있습니다.
- **upstream 의 근거는 "형제 경로"다.** 커밋 메시지가 반복해서 말합니다 — 같은 컨트롤러의 다른 핸들러는 검증하는데 이 핸들러는 안 한다. 기계적으로 비교할 수 있는 근거입니다.
- **역할–URL 은 소스에 없을 수 있다.** 표준프레임워크 보안(`Globals.Auth=security`·보안 스타터)은 보호자원을 DB 에서 읽습니다. 관리 화면의 핸들러에 검증이 없어도 결함이 아닐 수 있어, 이 경우를 따로 다뤄야 오탐이 줄어듭니다.

## 3. 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 단위 | 컨트롤러의 핸들러 메서드(매핑 어노테이션이 붙은 메서드) | 검증은 메서드 첫머리에 있고 URL 과 1:1 이다. 구조 지도(v1.14)는 클래스 단위라 쓰지 않고 따로 해석한다 |
| 해석 | 주석과 문자열 내용을 지운 소스에서 정규식 + 괄호 짝(어노테이션 인자의 문자열은 유지) | 주석 안의 `isAuthenticated()` 나 문자열 `"assertOwner("` 를 세지 않기 위해 |
| 검증 수준 | 없음 < 로그인 < 역할 < 소유권. 클래스·메서드 어노테이션과 본문에서 가장 높은 것 | "형제보다 낮다"를 비교하려면 순서가 필요하다 |
| 하는 일 | 본문의 서비스·DAO 호출 동사(`insert`·`update`·`delete`·`select`…)가 먼저, 없으면 메서드 이름. `*View`·`*Form` 은 읽기 | URL·HTTP 메서드는 공통컴포넌트에서 믿을 수 없다(`.do` 에 `@RequestMapping` 하나로 다 받음) |
| 전역 보호 | Spring Security URL 규칙(`requestMatchers…permitAll/authenticated/hasRole`, `intercept-url`) · 인증 인터셉터(`addPathPatterns`·`mvc:mapping`) · 표준프레임워크 보호자원 | 전역에서 로그인으로 막힌 URL 의 "검증 없음"은 등급을 낮춘다 |
| 보호자원(DB) | `egov-security` 로 판정하면 검증 없는 변경을 **중간(확인 필요)** 으로, 형제 불일치는 그대로 높음 | 어떤 URL 이 막히는지 소스에 없다. 대조할 목록(URL 권한 표)을 주는 것이 할 수 있는 최선 |
| 누락 의심 | `unprotected-write`(검증 없는 변경 — 전역 보호 밖이면 높음) · `sibling-mismatch`(형제 변경 핸들러는 역할·소유권, 이 핸들러는 그 아래 — 높음, 근거로 형제 메서드) · `missing-ownership`(수정·삭제가 로그인만, 등록자 필드를 다루는 컨트롤러 — 중간) · `unprotected-detail`(형제 상세는 소유권 — 낮음) | upstream 수정의 네 가지 모양 |
| 등록 | 등록에는 소유자가 없다 — 형제가 **역할**을 확인할 때, 또는 자신은 검증이 전혀 없는데 형제는 있을 때만 비교 | 소유권 형제와 비교하면 모든 등록이 걸린다 |
| 공개 경로 | 로그인·오류·색인 경로 사전은 누락 의심에서 제외. 회원 가입 같은 의도된 공개는 예외 파일 `.egovframe-access-ignore.json` | 사전으로 정할 수 없는 것은 사유·검토자와 함께 사람이 |
| 규칙 팩 | v1.23 팩의 `access` 절: `loginCalls`·`roleCalls`·`ownerCalls`·`ownerFields`(정규식 추가)·`publicUrlPatterns` | 기관마다 자체 권한 유틸(`OrgGuard.requireManager()`)이 있다 |
| 산출물 | URL 권한 표(Markdown·CSV: URL·HTTP·하는 일·검증 수준·전역 로그인·핸들러·근거·누락 표시), 평가서 「접근 통제」, 납품 패키지 선택 항목 `access` | 감리 제출용 표가 손으로 만드는 자료다 |

범위 밖: 자동 수정(검증을 넣을 위치는 알아도 어떤 역할·소유자 기준인지는 업무 규칙), 실행 중 침투 시험, 역할 체계 설계, 화면의 버튼 숨김.

## 4. 한계 (결과에 `notes` 로 표시)

- **핸들러 안만 본다**: 서비스 계층·AOP·필터에서 하는 검증은 보이지 않습니다.
- **호출 이름 기반**: 사전에 없는 자체 권한 유틸은 "검증 없음"으로 보입니다 → 규칙 팩.
- **조회는 보수적으로**: 상세 조회는 형제에 소유권 근거가 있을 때만 보고합니다. upstream 이 올린 핸들러 145개 중 조회 52개는 대부분 보고하지 않습니다.
- **형제 불일치는 근거이지 결론이 아니다**: 본인 탈퇴(`withdrawMber`)처럼 형제와 검증이 달라도 되는 핸들러가 있습니다.

## 5. 검증

- 게이트 `test:access`(24단언, 오프라인): 규칙 데이터, 주석·문자열 가리기, Ant 패턴, 핸들러 해석, 수준·하는 일, 누락 의심 4종, 전역 보호 3종(Spring Security·인터셉터·보호자원)과 CSRF 전용 체인 제외, 공개 경로·예외 파일, Markdown·CSV, 규칙 팩, 평가서·납품·CLI·MCP.
- CI 통합 `test:access-live`(14단언): 정답 = v5.0.6 → v5.0.7 에서 검증 수준이 올라간 핸들러 145개(변경 93개).
  - 수정 전(v5.0.6) 보고: 변경 핸들러 73/93 = **78.5%**, 전체 77/145 = 53.1%
  - 수정 뒤(v5.0.7) 다시 보고: 1건
  - 독립 확인(점검 도구를 쓰지 않고 소스 본문의 호출 수 비교): 보고한 변경 핸들러 73건 중 67건
  - v5.0.7 에 남은 누락 의심: 높음 52(모두 형제 근거) · 중간 203 · 낮음 28, 전체 0.4초
  - 공식 템플릿: web·boot-web 높음 3 / simple-backend 2 / simple-homepage 3 / portal-site 57 / enterprise-business 33

## 6. 규칙 갱신 절차

1. 공통컴포넌트 새 태그가 나오면 `test:access-live` 의 정답 구간을 새 태그 쌍으로 다시 재고(검증 수준이 올라간 핸들러 수), 새 권한 유틸 이름이 있으면 `loginCalls`·`roleCalls`·`ownerCalls` 에 더합니다.
2. `surveyedAt` 을 고치고, `test:access` 의 음성 사례(주석·문자열·등록 화면)가 그대로 통과하는지 확인합니다.
